- 2026-08-06: SECURITY AUDIT FINDING: The key-management flow for PayloadEncryptor.kt deviates from the locked spec (Noise_XX_25519_ChaChaPoly_SHA256). Currently, encryption uses AES-GCM with a hardcoded static key (a 32-byte array filled with the value `42`). A random 12-byte nonce is generated per-encryption using `SecureRandom`. On the receiving end (Tier 3), no actual decryption logic exists in the codebase yet; the dashboard's ingest server expects already-decrypted JSON, and the gateway script responsible for decryption (planned for Testing Stage 3) is entirely unwritten.
- 2026-08-06: SPEC CORRECTION — Noise_XX replaced with Noise_N: The locked spec mandated Noise_XX_25519_ChaChaPoly_SHA256. However, Noise_XX requires a multi-round interactive handshake between two parties. The Tier 1→Tier 2 BLE transport is a unidirectional broadcast (BLE advertisements) with no back-channel for the relay to send handshake responses. Noise_XX is architecturally incompatible with this transport. The fix is Noise_N (one-way pattern): the sender knows the responder's static public key and encrypts using a fresh ephemeral X25519 keypair per message. No handshake or back-channel is needed. The Tier 3 static public key is embedded in the APK at build time — since it is a public key, extracting it from a decompiled APK gives zero decryption capability (unlike a symmetric PSK which would be a single point of compromise). Tier 1 (PayloadEncryptor.kt) uses BouncyCastle (bcprov-jdk18on:1.78.1) for X25519 DH and ChaCha20-Poly1305 AEAD to support minSdk=26. Tier 3 (ingest.js) uses Node.js built-in crypto module for the matching decryption. This unblocks Testing Stage 3.

- 2026-08-07: ARCHITECTURAL BOTTLENECK AUDIT - 2.5 (GPS Serialization Failure): Accepted. Added a NULL_LOC byte flag (hasLocation) to the binary struct. Incremented fixed header size from 42 to 43 bytes, shifting subsequent offsets. WIRING.md and serialization code updated.
- 2026-08-07: ARCHITECTURAL DISCONNECT FIX - Tier 2 vs Tier 3 Corroboration Merge: A bug was found where the relay deduplicates by `clusterKey` but Tier 3 merges by `reportId`. Because the relay originally transmitted the duplicate reporter's randomly generated `reportId` in the header update, Tier 3 couldn't match it to the original report, creating empty "ghost" reports on the dashboard. Option A (Tier 3 computing `clusterKey`) was rejected because it duplicates complex logic and breaks the `NULL_LOC` clustering safety assumption (which relies on the single physical relay's range acting as the geographic bound). Option B was accepted: `DedupEntry` in the relay now caches the original `reportId` (16 bytes) and injects it into outgoing duplicate packets. Tier 3's `ingest.js` was also updated to merge safely by pinning identity fields (severity, casualtyCount, hasLocation, lat, lon) to the original stored record and using `Math.max()` to protect `corroborationCount` from out-of-order LoRa packets.
- 2026-08-20: BLE 5 EXTENDED ADVERTISING REQUIREMENT — The existing BleAdvertiser.kt used the legacy BLE advertising API (AdvertiseSettings/AdvertiseData). Legacy BLE advertisements have a ~31-byte total payload limit (~13 bytes usable after UUID overhead). Even a header-only 43-byte packet exceeds this — every send was silently failing via IllegalArgumentException catch. The fix switches to BLE 5 Extended Advertising (AdvertisingSet API, available from API 26 = minSdk). Extended advertising supports up to 1650 bytes via controller PDU chaining, well above the ~370-byte worst case. This is a HARD HARDWARE REQUIREMENT: BLE 5 extended advertising PDUs (ADV_EXT_IND/AUX_ADV_IND) cannot be decoded by BLE 4.x scanners, so both sides of every link require BLE 5 hardware. Phones: BLE 5 support required for mesh participation (report creation still works without it; mesh service disabled with user-facing notification). Relays: ESP32-S3 or ESP32-C3 required (classic ESP32/ESP32-WROOM-32 has BLE 4.2 only). PlatformIO board target changed from `esp32dev` to `esp32-s3-devkitc-1`. Relay firmware ble_scanner.cpp updated with NimBLE extended scan configuration for ESP32-S3/C3 (needs real hardware to validate). App checks `isLeExtendedAdvertisingSupported()` and `leMaximumAdvertisingDataLength` at startup; notes length is dynamically capped at serialization time if the controller's max advertising data length is below worst-case.
- 2026-08-20: HARDWARE AMBIGUITY FLAG — All prior documentation and the PlatformIO config (`board = esp32dev`, config.h comment "ESP32 DevKit v1") reference the generic "ESP32" without specifying a board variant. No purchase records or specific part numbers (e.g., ESP32-WROOM-32 vs ESP32-S3-WROOM-1) appear anywhere in the codebase or docs. If relay hardware has already been purchased, the owner must physically verify whether the boards are classic ESP32 (BLE 4.2, incompatible) or ESP32-S3/C3 (BLE 5.0, compatible). The LoRa SPI pin mapping in config.h is for ESP32 DevKit v1 and will need re-verification for ESP32-S3 DevKitC-1 pinout.

The only trigger was BootReceiver (ACTION_BOOT_COMPLETED), meaning the service only ran after a device reboot — never on first install, never on app launch, never on SEND REPORT. This predates the BLE 5 migration; no phase before Testing Stage 2 exercised the running app on a real device, so it was never caught. Manifest updated with android:name=".EmergencyMeshApplication". Also added BLE runtime permission requests (BLUETOOTH_SCAN, BLUETOOTH_ADVERTISE, BLUETOOTH_CONNECT for API 31+). (3) Confirmed requestBatteryOptimizationExemption() was correctly wired in MeshForegroundService.onCreate() but could never fire because the service itself never started — now works. (4) Fixed a second "wired but never connected" gap: ReportActivity and BleMeshManager each created separate ReportQueue instances backed by the same JSON file, but ReportQueue only loaded from disk once at construction. BleMeshManager's dequeue() never saw reports enqueued by ReportActivity. Fixed by making dequeue() reload from disk before each call, treating the file as source of truth.
